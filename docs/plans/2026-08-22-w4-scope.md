# W4 scope — smallest source-only dual-read slice

Status: **scope proposal, not authorization to build.** Revised after independent review; the
review's blocking finding is section 2. This document defines what W4 is and is not; it adds no
code.

Basis: `docs/plans/2026-08-20-tranche4-federation-storage-contract-freeze.md` § "W4 — dual-read
application and clean Vuoro catalog", W3 as merged (`227f55f`), and the pinned Vuoro tree at
`9dc7efa8d3f546851218f49da7653f806d5e8ca4`.

## 1. What W4 is

Add a separate `federation/v1` serving surface and catalog descriptor while retaining
`execution/v1` byte for byte, and coordinate the Vuoro composition in Vuoro's own repository and
pull request. W4 ends when the source and the composition validate; every live migration,
deployment, credential and role-fencing action is W5 and operator-owned.
<!-- claim: w4-source-only -->

## 2. Blocking decision: the manifest cannot express five domains today

**This must be settled before anything on the ActionQ side is built, and certainly before a wheel
is published.** The pinned Vuoro composition rejects a five-descriptor manifest in running
service code, not merely in a script:

- `composition.py:39` — `_REQUIRED_DOMAINS = frozenset({"work", "execution", "knowledge", "audit"})`,
  enforced at `:343` (`must pin exactly work, execution, knowledge, and audit`) and `:345`;
- `scripts/fetch_pinned_adapters.py:21,97,106` — the same four-domain constant, and the freeze
  doc's own W4 command block runs the *candidate tree's* fetch script;
- `scripts/attest_installed_composition.py:21,105` and `scripts/verify_pre_migration_startup.py:42`
  — the same constant again, the latter being the pre-migration startup gate.

Worse, two descriptors cannot share one wheel: `composition.py:332-336` rejects duplicate
distributions, and `:391-393` requires an adapter lock to be an exclusive primary, so
`federation` can neither declare a second `actionq` distribution nor reuse the execution lock.

Three ways out, and the choice is Vuoro's to make:

1. **Revise the manifest schema** to a `vuoro-composition/v4` permitting one adapter lock to be
   the primary of two descriptors. Most faithful to "exactly five descriptors"; largest change.
2. **Publish a second ActionQ distribution** for federation. Keeps the manifest schema frozen;
   splits one package into two artifacts with the release machinery that implies.
3. **Keep four manifest descriptors** and let ActionQ's single `register` entrypoint register
   both `owning_domain: "execution"` and `owning_domain: "federation"` operations. Cheap and
   legal today, but the *catalog* then has five domains while the manifest has four — which
   contradicts "registered separately" and weakens the isolation the freeze doc wants.

Until this is chosen, "exactly five descriptors" is unimplementable, and the sizing below is
provisional.
<!-- claim: w4-manifest-shape-undecided -->

## 3. The slice

**ActionQ side** — no modification of `execution/v1`:

1. a federation serving surface: a thin object over the merged `FederationAuthority`, in its own
   module (`actionq/vuoro_federation.py`), with its own `register` callable and its own
   compatibility record built from `federation_schema.check_compatibility`. Not inside
   `actionq/vuoro.py`: a descriptor names exactly one `adapter_module` + `register` pair, so
   putting federation registration in the execution adapter's module is the opposite of separate;
2. `tests/test_federation_catalog_contract.py`, which the freeze doc names and which does not exist;
3. a version bump and a tagged GitHub release — `pyproject.toml` is still `0.1.26`, the currently
   pinned wheel, and `tests/test_release_contract.py` / `test_release_version.py` are in the blast
   radius;
4. reachability-manifest entries for the new module, its import edges, its
   `catalog_operation_groups` and a `catalog_handler_bindings` row per federation operation.

**Vuoro side** — its own repository and pull request:

5. whichever manifest-shape change section 2 selects, plus the four-domain constant in
   `composition.py`, `fetch_pinned_adapters.py`, `attest_installed_composition.py` and
   `verify_pre_migration_startup.py`, and a per-domain construction block in
   `composition.py:1029-1069` (DSN env var, application object, register call, compatibility);
6. `validate_released_federation_composition.py`, proving **all five** things the freeze doc
   requires — five descriptors, legacy execution operation bytes/hashes, a changed global
   revision, federation actor ACL and expected-revision schemas, and stale-catalog rejection
   before any ActionQ write. Its baseline analogue is 300 lines and spins up the real ASGI app;
   that is the honest estimate, not a manifest shape check;
7. a re-run of `validate_released_execution_adapter.py` against the **new** wheel. Publishing for
   federation moves the execution descriptor's lock to a new artifact, so "execution/v1 is
   unchanged" must be re-proved against the artifact that will actually be deployed. The freeze
   doc runs that validator only against the baseline, which would leave the pinned operation
   hashes unchecked against the new wheel — exactly its own "old execution hashes drift" falsifier.

Nothing else. The dormant module gains no new commands and no migration is run anywhere.
<!-- claim: w4-slice-contents -->

## 4. What W4 must not do

`execution/v1` stays byte-for-byte identical — the same 26 operations by default, 27 with the
managed-dispatch policy, the same wire hash. The `federation/v1` catalog carries no claim, renew,
settle, sweep, managed-dispatch enqueue, group-control, harness, model or prompt field. Every
federation write definition must declare its idempotency key **required**: the authority raises
without a non-empty key, while the execution adapter tolerates absence and passes `""`. A served
`record_execution_ref` must shape its input so an external reference cannot carry a launch
instruction.
<!-- claim: w4-execution-v1-frozen -->

## 5. Two gates

The four-domain baseline at the literal pinned commit is never evidence for the five-domain
candidate, which is validated separately against a literal 40-hex SHA with every wheel fetched
from its canonical release URL and digest-verified.

## 6. Ordering, and why the design order is the reverse of the release order

The release order is fixed: merge source, publish the exact wheel, run the federation migration
with it, validate the candidate. The dormant source is already merged, so W4 owns the wheel
publish and the candidate validation; the migration is W5.

W4 validates the candidate *before* the migration runs, which inverts steps 3 and 4 of the frozen
order. That is defensible and must be stated rather than assumed: the candidate validators are
database-free by construction, so nothing about them requires a migrated schema. W5 still runs
the migration before any deploy, because `federation_schema.check_compatibility` reports
`uninitialized` until it does and the composition turns that into an incompatible domain at
startup.

The Vuoro candidate manifest must name a wheel digest that already exists — the fetch script
accepts only canonical release URLs with no local-path or dry-run escape — so the ActionQ change
merges and publishes before the Vuoro pull request can be validated. **But the design order is
the reverse.** A published release wheel cannot be amended; any ActionQ change after the Vuoro PR
opens costs a version bump, a new tag, a new release, a manifest edit and a full re-validate.
So the Vuoro manifest shape (section 2) must be settled *first*, the ActionQ surface built to fit
it, and only then published.
<!-- claim: w4-design-order-precedes-release-order -->

## 7. Rollback needs no ActionQ kill switch

Because the composition names the wheel and not the reverse, rolling Vuoro back to the
four-domain release un-serves `federation/v1` without touching the ActionQ artifact or the
federation schema. That satisfies the freeze doc's rollback requirement with nothing feature-
flagged in ActionQ — worth stating, because otherwise a reader looks for a switch the slice does
not contain and does not need.
<!-- claim: w4-rollback-is-vuoro-side -->

## 8. Resolved by the scope review

**The federation surface stands beside `ActionQApplication`, not inside it.** There is no
plumbing to duplicate: `FederationAuthority` takes only a connection factory and a schema and
does its own compatibility handshake. Reuse would be actively wrong — `ActionQCore.connection()`
asserts *execution* schema compatibility on every call, so a shared object would make every
federation call claim execution v12 readiness, which the freeze doc forbids in as many words.

**W4 serves the whole authority, not a read-only subset.** Serving only `snapshot` is not merely
cautious, it is unusable and unfalsifiable: `snapshot` requires a `resource_ref` and the authority
exposes no list or search, so a client has no served way to obtain one; and the required validator
assertions about ACL and expected-revision schemas would have no subject. Dormancy is a grants
question — authority is checked per command against the principal's authority set, so a served
write with no principal holding the authority is inert — and grants are what W5 fences. The cost
of narrowing is concrete: each later addition changes the global revision and forces every client
to rediscover.

**The stale-catalog check stays in Vuoro's dispatch, unchanged.** It already rejects a mismatched
revision before the handler runs, and nothing about that path is domain-specific. W4's deliverable
is the assertion in the federation validator, not a second check in the ActionQ adapter, which
would buy nothing.

## 9. Still open — decide during W4, not after

**How does a Vuoro `Identity` become a `FederationPrincipal`?** This is the largest undecided
item and it is not a naming question. Ownership equality turns on `principal_id` matching
`owner_principal_id` forever, and v1 has no ownership transfer. If the actor string that becomes
`principal_id` can ever be reissued or renamed, ownership silently transfers to a different
person, and the resulting data is unfixable. Decide the stable-identifier rule in W4.

Two smaller ones: whether federation operations are repository-scoped or plain authority-gated in
Vuoro's authorizer, which is execution-specific today; and who owns release-order steps 3 and 5–7
(Vuoro merge, release, deploy, client rediscovery, evidence capture), which no document currently
assigns.
