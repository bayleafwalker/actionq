# W4 scope — smallest source-only dual-read slice

Status: **scope proposal, not authorization to build.** Written per the recorded sequence
"scope the smallest W4 source-only slice → have that scope independently reviewed → build".
This document defines what W4 is and is not; it does not add code.

Basis: `docs/plans/2026-08-20-tranche4-federation-storage-contract-freeze.md` § "W4 — dual-read
application and clean Vuoro catalog", and W3 as merged (`227f55f`).

## 1. What W4 is

Add a separate `federation/v1` application surface and catalog descriptor while retaining
`execution/v1` byte for byte, and coordinate the Vuoro composition pins in Vuoro's own
repository and pull request.

A source release is not a deployment. W4 ends when the source and the composition validate;
every live migration, deployment, credential and role-fencing action remains W5 and is
operator-owned.
<!-- claim: w4-source-only -->

## 2. The smallest slice

Two repositories, deliberately not one change.

**ActionQ side** — three additions, no modification of `execution/v1`:

1. a federation application surface exposing the already-merged `FederationAuthority` commands
   as served operations;
2. a `federation/v1` catalog descriptor registered *separately* from the frozen `execution/v1`
   descriptor in `actionq/vuoro.py`, never as `execution/*` and never extending the 26-operation
   legacy catalog;
3. `tests/test_federation_catalog_contract.py`, which the freeze doc names as a W4 deliverable
   and which does not exist yet.

**Vuoro side** — its own repository, its own pull request:

4. composition pins naming the exact ActionQ wheel and its SHA-256;
5. `validate_released_federation_composition.py`, proving exactly five descriptors (`work`,
   frozen `execution/v1`, `federation/v1`, `knowledge`, `audit`).

Nothing else is in scope. In particular the dormant module gains no new commands, the legacy
catalog gains no operations, and no migration is run anywhere.
<!-- claim: w4-two-repository-slice -->

## 3. What W4 must not do

`execution/v1` stays byte-for-byte identical: the same 26 operations by default, 27 with the
managed-dispatch policy enabled, the same operation bytes and hashes. The `federation/v1`
catalog carries no claim, renew, settle, sweep, managed-dispatch enqueue, group-control,
harness, model or prompt field. Adding a fifth domain changes Vuoro's global catalog revision,
and every `federation/v1` invocation must send the exact discovered revision, with a mismatch
rejected as `stale-catalog` before authorization, handler or decision-ledger execution — so no
ActionQ write can occur under a stale catalog.
<!-- claim: w4-execution-v1-frozen -->

## 4. Two gates, not one

The immutable four-domain baseline is not evidence for the five-domain candidate. The baseline
proves the frozen `execution/v1` composition at the literal pinned Vuoro commit
`9dc7efa8d3f546851218f49da7653f806d5e8ca4`; the candidate must be validated separately against a
literal 40-hex commit SHA supplied by the coordinator. A branch, a tag, a working tree or a
symbolic `HEAD` is never source-revision proof, and every pinned wheel must be fetched from the
manifest's canonical release URL and digest-verified.
<!-- claim: w4-two-independent-gates -->

## 5. Sequencing and its one hard dependency

The freeze doc's release order is fixed: merge dormant source, build and publish the exact
wheel recording source SHA and artifact SHA-256, run the federation migration with that exact
wheel, then validate the five-domain candidate. W4 owns the first two steps and the candidate
validation; the migration run is W5.

The hard dependency runs the other way from how it first appears: the Vuoro candidate manifest
must name an ActionQ wheel that already exists, so the ActionQ-side change merges and publishes
*before* the Vuoro pull request can be validated, not alongside it.
<!-- claim: w4-actionq-precedes-vuoro -->

## 6. Backfill's place in the order

W3's import must complete before any native principal is granted `federation.create` in an
environment, because deterministic references are precomputable and `create` is first-writer-wins
with no delete and no ownership transfer. W4 introduces the first surface through which a native
principal could hold that authority, so this is the release where the ordering constraint stops
being theoretical.
<!-- claim: w4-backfill-precedes-native-create -->

## 7. Open questions for the scope review

These are genuinely undecided and should not be resolved by whoever builds W4 alone.

1. **Does the federation application reuse `ActionQApplication` or stand beside it?** Reuse risks
   the two domains sharing state and drifting into a single surface; a separate class duplicates
   connection, compatibility and provenance plumbing. The freeze doc requires separateness of the
   *catalog*, and is silent on the application object.
2. **Which federation commands are served in W4 at all?** The narrowest reading serves only reads
   (`snapshot`), which is enough to prove a five-domain composition without exposing any write
   path before W5's role fencing exists. The widest serves every command the authority has.
   Narrow is safer and may be too narrow to be a useful gate.
3. **Where does the stale-catalog check live** — in Vuoro's dispatch, in the ActionQ adapter, or
   both? The freeze doc requires the rejection to happen before any ActionQ write, which the
   adapter alone cannot guarantee.
